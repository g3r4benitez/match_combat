# Contract: Alembic Migration CLI

**Feature**: 006-alembic-migrations
**Date**: 2026-09-21
**Contract Type**: CLI / Infrastructure interface

## Overview

This feature does not introduce a web API endpoint. Instead, it establishes a **CLI contract** for database migration tooling that developers use to evolve the schema. The contract defines the commands, their inputs, expected effects on the database, and the migration script format.

All commands are run from the **project root** (where `alembic.ini` lives) so the `app` package is importable via `prepend_sys_path = .` in `alembic.ini`.

## Command Contract

### 1. Generate a Migration

**Command**: `alembic revision --autogenerate -m "<message>"`

**Input**:
- `-m "<message>"`: Human-readable revision message (required)
- `--autogenerate`: Flag to compare models against database and produce candidate operations

**Effect**:
- Creates a new file in `alembic/versions/` with a partial GUID revision ID.
- File contains `revision` and `down_revision` identifiers, `upgrade()` and `downgrade()` functions.
- Candidate operations are placed inside `### commands auto generated by Alembic ###` markers.

**Output on success**:
```
INFO  [alembic.env] Running upgrade  <base> -> <new_rev>
Generating /path/to/alembic/versions/<rev>_<slug>.py...done
```

**Post-generation responsibility**: Developer MUST review the generated file and adjust if autogenerate missed manual changes or produced incorrect diffs.

---

### 2. Apply Pending Migrations

**Command**: `alembic upgrade head`

**Input**:
- `head`: Target revision = latest available

**Effect**:
- Reads `alembic_version` table to determine current revision.
- Applies `upgrade()` of all pending revisions in dependency order.
- Creates `alembic_version` table if not present.
- Each revision runs in its own transaction.

**Output on success**:
```
INFO  [alembic.env] Context class SQLiteContext.
INFO  [alembic.env] Will assume non-transactional DDL.
INFO  [alembic.env] Running upgrade  <current> -> <target>
```

**Error behavior**: If a migration fails mid-execution, Alembic rolls back that migration's transaction. The database remains at the last successfully applied revision.

---

### 3. Rollback Migrations

**Command**: `alembic downgrade -1` (one step) or `alembic downgrade <rev>` (to specific)

**Input**:
- `-1` / `-2`: Rollback N steps
- `<rev>`: Target revision identifier (or `base` to rollback all)
- `base`: Rollback to empty database

**Effect**:
- Runs `downgrade()` functions in reverse dependency order.
- Updates `alembic_version` table to reflect new current revision.

**Output on success**:
```
INFO  [alembic.env] Running downgrade  <current> -> <target>
```

---

### 4. Inspect State

| Command | Effect |
|---------|--------|
| `alembic current` | Print current database revision |
| `alembic history` | Print all revision identifiers and messages |
| `alembic branches` | Print branch points |
| `alembic heads` | Print head revision(s) |
| `alembic show <rev>` | Show details of a specific revision |

---

### 5. Adopt Existing Database (Stamp)

**Command**: `alembic stamp head`

**Input**: None (target is `head`)

**Effect**:
- Creates `alembic_version` table and sets it to `head` **without running any DDL**.
- Used when the database schema already matches the models (e.g., created by `create_all`).
- This is the migration path for existing `match_combat.db` files.

---

### 6. CI Drift Detection

**Command**: `alembic check`

**Input**: None

**Effect**: Compares `target_metadata` (SQLModel models) against the reflected database schema at current revision.

**Output on success** (no drift):
```
No metadata to cycle yet.
```
(exit code 0)

**Output on failure** (drift detected, exit code 1):
```
INFO  [alembic.autogenerate.compare] Detected added table '...'
...
```

**Usage**: Add to CI pipeline to enforce that models and migrations stay in sync.

## Migration Script Format Contract

Every migration file in `alembic/versions/` must conform to this structure:

```python
"""<descriptive message>

Revision ID: <partial-guid>
Revises: <parent_rev_or_empty>
Create Date: <timestamp>

"""
from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic.
revision = '<partial-guid>'
down_revision = '<parent_rev_or_None>'
branch_labels = None
depends_on = None


def upgrade() -> None:
    """Apply the schema change."""
    # --- commands auto generated by Alembic - please adjust! ---
    # <operations here>
    # --- end Alembic commands ###


def downgrade() -> None:
    """Revert the schema change (opposite of upgrade)."""
    # --- commands auto generated by Alembic - please adjust! ###
    # <reverse operations>
    # --- end Alembic commands ###
```

**Rules**:
- `revision`: Auto-generated 12-char hex partial GUID; must be unique.
- `down_revision`: Points to the parent revision (or `None` for the first migration). Forms the dependency chain.
- `upgrade()`: Must be the exact inverse-capable forward operation.
- `downgrade()`: Must reverse every operation in `upgrade()`. **Always required** for rollback support.
- All Alembic operations use `op.*` (e.g., `op.add_column`, `op.create_table`, `op.drop_table`).
- Manual data migrations are added **outside** the `### commands auto generated ###` block.

## env.py Interface Contract

The `alembic/env.py` file must provide:

1. **`target_metadata = SQLModel.metadata`**: The shared metadata containing all table definitions. All model modules must be imported before this assignment.

2. **Database URL resolution**: Must read from `app.core.config.DB_URL` (single source of truth with the application). The `alembic.ini` `sqlalchemy.url` is overridden at runtime.

3. **Configuration parameters**:
   - `compare_type=True`: Detect column type changes.
   - `render_as_batch=True`: Enabled only when `dialect.name == "sqlite"`.

4. **`run_migrations_offline()`**: For SQL-only generation (`--sql` flag). Uses `url` parameter, `literal_binds=True`, `dialect_opts={"paramstyle": "named"}`.

5. **`run_migrations_online()`**: For live database operations. Creates an engine via `engine_from_config`, opens a connection, and configures the migration context with the detected dialect.

| Columns | `version_num` (String(32), single row) |
| Managed by | Alembic (auto-created on first migration) |
| Application access | None — internal to Alembic |
| Purpose | Tracks which revision the database is at |

## Command Reference Summary

```text
alembic <command> [options]

Commands:
  upgrade/revision/downgrade/stamp/current/history/branches/heads/show/check

Key options:
  -m "<message>"    Revision message (required for revision)
  --autogenerate    Generate candidate ops from model diff
  head              Target: latest revision
  base              Target: empty database
  -1, -2, +1, +2    Relative revision steps
  <rev>             Partial revision identifier
  --sql             Output SQL instead of executing
  -x key=value      Extra args passed to env.py
  --config PATH     Alternative alembic.ini path
```

## Environment Variables

| Variable | Purpose | Default in `.env` |
|----------|---------|--------------------|
| `DB_URL` | Database connection URL | `sqlite:///./match_combat.db` (dev) |
| `DB_USER` / `DB_PASSWORD` / `DB_HOST` / `DB_PORT` / `DB_NAME` | PostgreSQL connection components (used by `get_database_url()` fallback) | See `.env.example` |

**Note**: After this feature, `config.py` will prefer the `DB_URL` env var directly (see research.md R-004), so both the app and Alembic share one URL.
