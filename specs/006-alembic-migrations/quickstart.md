# Quickstart: Alembic Migrations

**Feature**: 006-alembic-migrations
**Date**: 2026-09-21
**Prerequisites**: Existing match_combat project with SQLModel models in `app/models/`, Python 3.11+

## New Dependencies

```bash
pip install alembic==1.20.0
```

Add to `requirements.txt`:
```
alembic>=1.20.0
```

## Files to Create

| File | Purpose |
|------|---------|
| `alembic.ini` | Alembic CLI configuration (generated by `alembic init`) |
| `alembic/env.py` | Migration environment: database URL + SQLModel metadata wiring |
| `alembic/script.py.mako` | Migration script template (generated) |
| `alembic/versions/` | Directory for migration scripts (starts empty) |
| `alembic/env.py` model imports | Must import all models so `SQLModel.metadata` is populated |

## Files to Modify

| File | Change |
|------|--------|
| `app/models/__init__.py` | Add naming convention to `SQLModel.metadata` (must run before model definitions) |
| `app/core/config.py` | Honor `DB_URL` env var directly: `DB_URL = _config("DB_URL", default=get_database_url())` |
| `app/core/database.py` | Replace `SQLModel.metadata.create_all(engine)` with `alembic upgrade head` in `init_db()` |
| `requirements.txt` | Add `alembic>=1.20.0` |
| `Dockerfile` | Update Python version from 3.9 to 3.11 (matches local dev) |

## Implementation Steps

### Step 1: Install and Initialize Alembic

```bash
pip install alembic==1.20.0
alembic init alembic
```

This creates `alembic.ini`, `alembic/env.py`, `alembic/script.py.mako`, and `alembic/versions/`.

### Step 2: Configure `alembic.ini`

Edit `alembic.ini`:
```ini
# Ensure app package is importable
prepend_sys_path = .

# Placeholder — env.py reads the real URL from app.core.config
sqlalchemy.url = sqlite:///placeholder
```

### Step 3: Configure `alembic/env.py`

Key settings in `env.py`:
- Import all model modules so `SQLModel.metadata` is populated
- Set `target_metadata = SQLModel.metadata`
- Read DB URL from `app.core.config.DB_URL`
- Enable `compare_type=True`
- Enable `render_as_batch=True` only for SQLite (`dialect.name == "sqlite"`)

> See `research.md` R-002 and R-003 for the exact `env.py` code pattern.

### Step 4: Add Naming Convention

In `app/models/__init__.py` (currently empty), add a naming convention to `SQLModel.metadata` so unnamed constraints get deterministic names. This is required for SQLite batch mode to work correctly on schema changes involving foreign keys.

> See `research.md` R-006 for the exact convention and code.

### Step 5: Generate Initial Migration

```bash
# Against a clean database (no existing tables)
alembic revision --autogenerate -m "initial schema"
```

Review the generated file in `alembic/versions/` — it should contain `op.create_table(...)` calls for all 10 entities. Adjust if needed, then apply:

```bash
alembic upgrade head
```

### Step 6: Replace `create_all` in `init_db()`

In `app/core/database.py`, replace `SQLModel.metadata.create_all(engine)` with an Alembic upgrade call so the app self-initializes at startup:

```python
def init_db():
    alembic_cfg = Config("alembic.ini")
    command.upgrade(alembic_cfg, "head")
```

For existing dev databases (already created via `create_all`, now matching models):
```bash
alembic stamp head   # mark as migrated without re-running DDL
```

## Validation Scenarios (End-to-End)

### Scenario 1: Fresh Database Initialization (SC-002, SC-003)

**Prerequisite**: No existing database file.

```bash
# Remove any existing dev database
rm -f match_combat.db

# Apply all migrations from scratch
alembic upgrade head

# Verify schema was created
alembic current
# Expected: <revision_id> (head)
```

**Expected outcome**: All 10 tables created (`competidor`, `match`, `modalidad`, `sexo`, `evento`, `area`, `entrada`, `user`, `tokenblacklist`, `passwordresettoken`) plus `alembic_version`. Exit code 0.

### Scenario 2: Migration Drift Detection (CI Gate)

```bash
# After starting the app (which calls init_db -> alembic upgrade head)
alembic check
# Expected: "No upgrades to render" (exit 0) — models match migrations

# Now modify a model, e.g., add a field to Competidor
# Then run:
alembic check
# Expected: "Detected added column 'competidor.new_field'" (exit 1) — drift detected
```

### Scenario 3: Generate Migration from Model Change (SC-001)

```bash
# 1. Modify a model (e.g., add a column to Competidor in app/models/competidor.py)
# 2. Generate a migration
alembic revision --autogenerate -m "add new_field to competidor"

# 3. Review the generated file
cat alembic/versions/<rev>_add_new_field_to_competidor.py
# Expected: contains op.add_column('competidor', sa.Column('new_field', ...))

# 4. Apply the migration
alembic upgrade head

# 5. Verify
alembic current
# Expected: new revision at head
```

**Expected time**: <30 seconds for generation and application.

### Scenario 4: Rollback (SC-004)

```bash
# Assuming Scenario 3 was completed
alembic downgrade -1
# Expected: Runs the downgrade() function, reverts the column addition
# Expected time: <30 seconds

alembic current
# Expected: previous revision
```

### Scenario 5: Migration History Query (SC-005)

```bash
alembic history --verbose
# Expected: Lists all revisions with timestamps, revision IDs, and messages
# Expected: Shows applied revisions in chronological order
```

### Scenario 6: Full App Startup (Integration)

```bash
# After completing all implementation steps
python -m uvicorn app.main:app --reload

# Expected: App starts without error (init_db runs alembic upgrade head at startup)
# Expected: All endpoints functional, database schema matches models
```
